# 舊客單搬遷與付款分階段對應

本階段為 owner-only 唯讀預覽，不會將 PL2 訂單匯入營運資料表，不修改 Sheets／Notion，不觸發同步或客人通知。

## 對應規則

| PL2 欄位／證據 | PL3 對應 | 核對要求 |
|---|---|---|
| 訂單編號 + Notion 原始頁面 + 最後更新 | 來源身分與版本 | 不依姓名或 Email 合併；重複身分拒絕整批 |
| 訂單明細的所屬訂單 Notion URL | 原單商品關聯 | 正規化 Notion page ID；孤兒明細列出；缺明細不准搬遷 |
| 商品款 | 一補應收 | 明細數量×單價須相符 |
| 二補金額 | 二補應收 | 空白是未定；0 是來源明示零元；不能據此推定已有收款 |
| 第一階段已核對 + 入帳金額 | 一補已核實款項 | 缺金額需人工確認；超額留未分配額度 |
| 付款資料已提交 | 待核對回報 | 不分配為入帳 |
| 第二次付款已核對 | 二補待補收款歸屬證據 | 不把同一個匯款金額再套用到二補 |
| 官方付款確認信 | 指定訂單／階段收款證據 | 原始來源狀態仍保留，不覆寫 |
| 一補尾款轉二補 | 尾款移轉記錄 | 必須指定二補原值是否已含尾款，防止加兩次 |
| 明確貨到付款約定 | 商品款 COD | 配送方式本身不能證明 COD；平台實際撥款才結清 |
| 黑貓運費到付 | 運費付款方式 | 不等於商品款 COD |
| 合併付款通知 | 多張既有帳款的集合 | 不生成第二份應收，不合併訂單 |
| 溢付款 | 未分配額度 | 不自動抵二補；跨單分配需授權證據 |
| 取消／撤單／撤回／售罄 | 排除搬遷 | 不恢復訂單 |
| 採購延後決定 | 獨立 hold 與截止日期 | 不因舊付款或商品狀態解除；須保留品項範圍 |

## 使用

主購測試工作台展開「舊客單搬遷與一補／二補／貨到付款對應」，貼入去識別 JSON 後核對。來源不得包含姓名、Email、帳戶資料。32 KB／批，上限100張單、500筆明細。預覽不持久化；清除或登出即移除畫面資料。

`POST /api/admin/legacy-payments/preview` 僅 owner 可用，沿用 cookie 同源防護。所有結果 `safe_to_import:false`；`ready_for_review` 只是基本資料齊備，並非已核准切換正式環境。

實作：`legacy-payment-mapper.js`、`payment-ledger.js`。帳務配置檢查：重複 allocation／超額配置／未核對回報／跨單未授權／COD未撥款均拒絕。原有 QA 收款審核及正式同步仍保留原本隔離限制，尚未接入實單寫入。
